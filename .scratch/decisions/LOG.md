Beaten options: a `TenantSettings` table (keeps `Tenant` genuinely unreachable but costs a join, a second row whose absence is a new failure mode, and turns issue 07's criterion 1 from an assertion about **database defaults** into one about seeded rows — the shape the human had already rejected when choosing 046); and a `SECURITY DEFINER` function (preserves the invariant verbatim, but record 031 reserved that mechanism for a **third pre-auth lookup** and this is an ordinary authenticated read, so it brings the heavier tool to the lighter problem and a body that bypasses RLS is harder to review than a two-line policy). The amended assertion must get **stronger, not weaker** — exactly one row returned and it is the caller's own; another tenant's row invisible **including when addressed directly by id**, proven readable elsewhere first; an unscoped connection still reading **zero**; and `deanpos_app` still holding no `DELETE`, with `UPDATE` unable to move a row across tenants — the last two being what a careless amendment drops. Reversal is dropping both policies and moving the settings to their own table, which needs a **backfill** and therefore human escalation; **the cost rises the moment a real deployment exists**, not gradually. Reverse it if any tenant-scoped connection ever needs to read a `Tenant` row that is not its own, if a second unrelated reason to grant `UPDATE` appears, or if `Tenant` gains a **platform-owned** column — a billing plan, a suspension flag, a trial expiry — which own-row `UPDATE` would let a tenant rewrite.
